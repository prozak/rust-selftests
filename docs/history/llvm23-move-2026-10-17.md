# LLVM 23 move (2026-10-17)

The toolchain behind every object moves from LLVM 22.1.8 / rustc 1.96.1 to
LLVM 23.1.4 (release/23.x `0cd28174a1f6` plus `patches/llvm/`) / rustc 1.99.1
(LLVM 23.1.1). Plan: `heimdall_experiment/next-session-prompt-llvm23.md`,
option B.

## Why from source

The release tarballs crash in `BPFAbstractMemberAccess::replaceWithGEP` on an
unused `llvm.bpf.preserve.field.info` call (issue #49), which rustc leaves
behind whenever it makes a `#[btf]` field access dead. The fix
(`patches/llvm/0001-*.patch`, upstream pull request pending from
prozak/llvm-project `bpf-unused-field-info`) is cherry-picked onto
release/23.x by `scripts/build-llvm.sh`; `scripts/fetch-llvm.sh` refuses to
run while `patches/llvm/` is not empty. Build: clang + lld, X86 + BPF,
Release, 40 minutes on 32 CPUs, 2.5 GB installed.

`rust-toolchain.toml` pins rustc 1.99.1 (`rustc` was unpinned before, and a
plain `rustup update` would have moved the bitcode to LLVM 23 under the
22.1.8 tools). rust-bpf's `bld_deps`, `libbtf_macros.so` and `bpf-postproc`
are rebuilt with the same rustc and LLVM (the last two had to be deleted
first: rust-bpf's rules track sources, not the compiler, and a proc macro
built by another rustc fails with E0514).

The C oracle moves too: `scripts/build-qemu-selftests.sh` compiles the
selftests with `LLVM_PREFIX`'s clang, so the selftests output and bpftool
were rebuilt with clang 23. No C object is byte-identical across the two
compilers; one object is new (`data_in_arena_rust.bpf.o`: upstream now
carries a Rust program of its own).

## What the move broke, and the fixes

### BTF prototypes follow the IR return type (LLVM 29b36a16f111)

Since LLVM 23 the BPF backend voids a function's BTF `FUNC_PROTO` return
when the LLVM function returns void ("ABI-accurate BTF prototypes for
DW_CC_nocall", which also drops optimized-away parameters of static C
functions). Three consequences:

- `BPF_NAKED` aggregate-return functions: `scripts/naked_abi.py` drops the
  Rust `sret` pointer, leaving a void function, so every struct/`u128`
  return in `aggregate_ret_func` vanished from BTF. Fix: the dropped
  `sret(T)` becomes the LLVM return type `T`.
- Static Rust functions whose result the caller discards: rustc's
  dead-argument elimination already made them return void in IR (25
  objects, 48 functions, see the scan in the session notes); LLVM 22 kept
  the debug-info return type in BTF, LLVM 23 does not. Only tail-calling
  subprograms care (`tail_call is only allowed in functions that return
  'int'`): `tailcall_bpf2bpf_hierarchy3` now consumes `subprog_tail`'s
  results like the C's `__sink()`.
- The C oracle's static functions lose optimized-away parameters:
  `test_pkt_access_subprog2(int val, skb)` is `(skb)` in BTF, and
  `fexit_bpf2bpf.c` reads the return value from slot 1 under
  `#if __clang_major__ >= 23`. `fexit_bpf2bpf.rs` follows.

### Rust `char` is an INT now

LLVM 22 dropped Rust's `char` (DW_ATE_UTF) base type, which turned
`*mut char` into a BTF `void *`; translations used that for C `void *`
(the `c_void` enum is not an option, see `test_attach_probe.rs`). LLVM 23
emits `INT 'char' size=4`, and 10 objects grew a `char *` that broke
skeleton compilation (`arena_htab`: `struct htab *` from `char *`).
`scripts/btf_rename.py` now always normalizes pointers to the 4-byte
`char` to `void *`.

### clang 23 enables `#if __clang_major__ >= 23` programs

The oracle gained programs the LLVM-22 oracle compiled out, and the
translations' explicit fallbacks (`dummy_test`) had to go:

- `aggregate_ret_func`: `global_ret_struct_ptr` / `global_ret_union_ptr`
  (+2 programs).
- `aggregate_ret_kfunc_arena`: four programs calling kfuncs that return
  16-byte aggregates in R0:R2. rustc's C ABI returns such a struct through
  a hidden pointer, so the kfunc is declared as returning `u64` (add_ksyms
  mirrors the real kernel prototype onto the declaration) and R2 is read
  with `asm!("", out("r2") v)` right after the call. A kfunc called only
  from inline asm gets no BTF prototype (the backend emits them for real
  call instructions), so the `__kfunc_btf_root` anchor of
  `aggregate_ret_kfunc.rs` does not transfer: the opt stage's keep list is
  the C object's global symbols.
- `arena_kfunc`: `arena_arg_stack` (a sixth argument, LLVM 23's stack
  argument through `r11`) and `arena_arg_stack_after_pair` (a by-value
  struct argument, spelled as two `u64`s).

### Tests that fail on the pristine C oracle

- `verifier_stack_arg` (clang-23-only, bundled in `prog_tests/verifier.c`
  which consumes many translated objects): "pruning with different stack
  arg types" expects `arg JOIN insn 9 -> 10 ... fp0-8 + _`, the kernel at
  645f5fcf says `insn 8 -> 10 ... _ + fp0-8`. Added to
  `scripts/known-bad-tests`.
- `known-bad-tests` entries now also reach test_progs as its `-d` glob
  denylist (whole-name match): `-t` matches substrings, so an object's
  own name (`stack_arg`, `arena`) pulled the denied test back in. The
  list travels as a `@.test-deny` file: subtest names carry spaces and
  `>`, which the kernel command line (where vng puts the guest command)
  mangles into a broken init path, and a whole gate ran on panicking
  guests before that was understood.
- `exceptions`: attaching exceptions_ext's `extension` to exceptions.bpf.o's
  `global_subprog` fails on the pristine clang-23 objects with "subprog() is
  not a global function" (the kernel resolves the target to the static
  subprog). The subtest name "non-throwing extension -> non-throwing
  subprog" is denied; its twin that expects -EINVAL goes with it.
- `stack_arg_precision` (clang 23 only, selected by substring from the
  stack_arg translations): "precision backtracking across bpf2bpf call for
  kfunc" expects a `mark_precise` line this verifier does not print. Denied.
- Lesson: never edit the gate environment scripts while a gate runs. bash
  reads a script incrementally, and the first gate's `test_d_path*`,
  `test_endian` and a dozen other rows failed with "unexpected EOF" from a
  half-edited `gate-overlay.sh`.

### Stack arguments reach the Rust objects

LLVM 23 passes a call's sixth and later arguments through `r11`, and the
verifier sizes a callee's incoming area from its BTF prototype. rustc's
argument promotion can give a static function more IR parameters than its
debug signature (`test_xdp_noinline`'s `encap_v4(pckt: &PacketDescription)`
became two loaded fields: six IR parameters, five in BTF, "invalid read from
stack arg off 8 depth 0"), and inter-procedural constant folding can give it
fewer (`stack_arg`'s `func_with_ptr_stack_arg`: 9 against 10). clang avoids
the mismatch by marking static functions `DW_CC_nocall`, which makes LLVM 23
emit the surviving parameters; rustc has no such thing. New
`scripts/stack_args.py` fails the build on the mismatch; `test_xdp_noinline`
launders `pckt` through `sink`, `stack_arg` reads the struct fields with
`read_volatile`.

`stack_arg` and `stack_arg_kfunc` were translated from the C's `#else`
fallback (no `__BPF_FEATURE_STACK_ARGUMENT` under LLVM 22) and are now the
real thing: 89 `r11` instructions in `stack_arg`, same as the C.

The prover does not model `r11`: it bails ("stack-argument register r11")
on `arena_kfunc`'s two stack-argument programs and on `stack_arg` /
`stack_arg_kfunc` instead of crashing with an IndexError (ERROR rows).

### Parameter decl tags

`bpf_rs_core::arg_tags!` declares the C's `__arg_nonnull` / `__arg_ctx` /
... on a function's parameters; `scripts/btf_test_tags.py` appends the
`BTF_KIND_DECL_TAG`s with the parameter index as `component_idx`.

### Verifier-complexity regressions

`pyperf180` (1M processed insns, 151k with LLVM 22) and `pyperf600_nounroll`
("The sequence of 8193 jumps is too complex", 445k insns before) stopped
verifying: same source, different register allocation and loop layout. The
verifier at 645f5fcf explores loops with a loop_stack/SCC walk; veristat in
the guest (`veristat -v -l2`) shows it holding about four branch states per
iteration for all 600 iterations without resolving them, where the C and
the LLVM 22 build exit the loop per path. Fixes:

- `pyperf180` and `pyperf600_nounroll` now spell `__get_frame_data` the
  way the C does: a `__weak` global subprog with `__arg_nonnull` on the
  three pointer parameters (`arg_tags!`), which the verifier checks once
  instead of per iteration (pyperf180: 776k insns). The six other pyperf
  variants keep the inlined form; they pass and were left alone.
- `pyperf600_nounroll` additionally builds at `opt-level=1` through the new
  `// RUSTC_OPT_LEVEL:` per-object annotation (Makefile): 502k insns, like
  the C's 466k. Backend flags (`-tail-dup-placement`, `-tail-dup-size`,
  `-disable-block-placement`, `-O1` in llc) change nothing; the shape comes
  from the middle end.

### Still there

- #59 (relaxed 32-bit `atomicrmw and/or/xor` fetch miscompile): present in
  23.1.4 and main 24.0.0git f3917db52
  (`heimdall_experiment/llvm-issue-bpf-i32-atomic-fetch.md`).
- rustc 1.99.1's `function_casts_as_integer` lint warns on the `f as usize`
  asm anchors.

## Unblocked by the fix (#49, #60, type_cast)

- `getsockname_unix_prog`, `getpeername_unix_prog`, `recvmsg_unix_prog`:
  the parked `bpf_core_cast` translations (branch
  `llvm23-unix-rdonly-cast`, 3ae163b) replace the `bpf_probe_read_kernel`
  stand-ins; the three prover waivers are gone (#49).
- `stream`: `user_vm_start` is read through a `#[btf]` view of the kernel's
  `struct bpf_arena` (a CO-RE relocation) instead of the hand-encoded
  offset that every pin bump had to re-check (#60).
- `type_cast`: translated (#16 parked draft redone): `bpf_rdonly_cast` with
  `BTF_TYPE_ID` ids and `#[btf]` field reads, no `bpf_probe_read_kernel`
  stand-in.
- `stack_arg`'s `global_dynptr_stack_arg` carries the C's `arg:ctx` on a
  `void *` parameter (`arg_tags!` + `BTF_C_VOID`).

verdict across the toolchain move. The gate took 1631 s with eight workers.
